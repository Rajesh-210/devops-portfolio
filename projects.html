Three-Tier Application on AWS EKS

Kubernetes Terraform Jenkins Docker AWS EKS Nginx

Problem Statement

The team needed to deploy a scalable three-tier microservices architecture (React frontend, Node.js backend, PostgreSQL database) with zero-downtime releases, environment parity across dev/staging/production, and full automation from code commit to production.

Solution Architecture

Designed and implemented a complete infrastructure and deployment pipeline using modern DevOps practices:

  • Infrastructure as Code: Modular Terraform configurations for VPC (public/private subnets, NAT gateways, route tables), EKS cluster, managed node groups, ECR repositories, and IAM roles.
  • CI/CD Pipeline: Jenkins pipelines triggered by GitHub webhooks → automated build, test, Docker image creation, push to ECR, and Kubernetes deployment manifests generation.
  • Kubernetes Orchestration: Deployed on EKS using Deployments, Services, Ingress (ALB), ConfigMaps, Secrets, and HPA for traffic-based auto-scaling.
  • Networking: Nginx as reverse proxy with TLS termination, internal load balancing, and rate limiting.

Key Technical Decisions

Terraform Remote State + DynamoDB Locking

Enabled safe, concurrent infrastructure changes across the team with full audit trail and state consistency.

ArgoCD GitOps Integration

After Jenkins builds, ArgoCD handles sync from Git to cluster — ensuring cluster state always matches Git (single source of truth).

Rolling Updates with Readiness/Liveness Probes

Zero-downtime deployments validated by health checks before traffic routing.

Results & Impact

83% Deployment Time Reduction
60% Release Cycle Improvement
0 Manual Deployment Errors

GitOps Deployment with ArgoCD

ArgoCD Helm Kubernetes GitHub

Problem Statement

Manual kubectl apply workflows led to configuration drift, lack of audit trails, and no rollback mechanism. The team needed a declarative, version-controlled approach where the Git repository is the single source of truth for all cluster state.

Solution Architecture

  • ArgoCD Installation: Deployed via Helm chart with HA configuration, RBAC, and SSO integration.
  • Application Definitions: Created ArgoCD Application resources pointing to GitHub repo paths for each microservice.
  • Auto-Sync & Self-Heal: Enabled automated sync with prune and self-heal — any drift from Git is automatically corrected.
  • Helm Charts: Packaged K8s manifests as Helm charts with environment-specific values.yaml for dev/staging/prod.
  • Progressive Delivery: Integrated with Argo Rollouts for canary/blue-green deployments.

Key Technical Decisions

App-of-Apps Pattern

Root Application manages child Applications — single point of control for entire platform bootstrap.

Declarative Project & RBAC Setup

Projects define source/destination permissions; teams only deploy to their namespaces.

Sync Windows & Waves

Controlled deployment order and timing to prevent dependency conflicts during releases.

Results & Impact

100% Audit Trail Coverage
0 Configuration Drift
10min Rollback Time
argocd-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: three-tier-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/Rajesh-210/k8s-manifests
    targetRevision: HEAD
    path: .
    helm:
      valueFiles:
        - values-prod.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      allowEmpty: false
    syncOptions:
      - CreateNamespace=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m

Monitoring & Alerting System

Prometheus Grafana Kubernetes Helm

Problem Statement

Running production workloads without observability meant incidents were detected late, root cause analysis was slow, and there was no proactive alerting. The team needed full-stack visibility into cluster health, application performance, and business metrics.

Solution Architecture

  • Prometheus Stack: Deployed via kube-prometheus-stack Helm chart — includes Prometheus Operator, Alertmanager, Grafana, Node Exporter, kube-state-metrics.
  • Custom Dashboards: Built Grafana dashboards for: cluster overview, pod/container metrics, node resources, application latency/error rates, and business KPIs.
  • Alerting Rules: Configured Alertmanager with tiered alerts — critical (pages), warning (Slack), info (email). Covered: pod crash loops, OOM kills, CPU throttling, disk pressure, API latency, error budgets.
  • Log Aggregation: Integrated Loki for log querying alongside metrics.

Key Technical Decisions

Multi-Tenant Prometheus with Federation

Central Prometheus federates from per-namespace Prometheus instances for scale and isolation.

SLO-Based Alerting

Alerts based on error budget burn rate rather than static thresholds — reduces noise.

Dashboard as Code

All dashboards version-controlled as JSON, deployed via ConfigMaps — changes reviewed in PR.

Results & Impact

70% Faster Incident Detection
15min Mean Time to Detect
4 Key Dashboards Built
PrometheusRule (alerts)
groups:
- name: k8s-alerts
  rules:
  - alert: PodCrashLooping
    expr: rate(container_restart_count[5m]) > 0
    for: 2m
    labels:
      severity: critical
    annotations:
      summary: "Pod {{ $labels.pod }} crash looping"
      description: "Restart rate > 0 in last 5m"

  - alert: CPUThrottlingHigh
    expr: (rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m])) > 0.25
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "High CPU throttling on {{ $labels.pod }}"
