A real war story — how we detected, triaged, and recovered from a Kubernetes cascade failure in 15 minutes.

Incident Timeline
T+0
02:14 AM — Alert Triggered
Prometheus fires critical alert: CPU throttling > 85% on prod-eks-worker-3
[PAGE] On-call engineer notified via Slack
T+2
02:16 AM — Triage Begins
Engineer joins incident bridge. Confirms node is NotReady. Pod crash loops detected in payment-service.
kubectl describe pod payment-service-7d8f9 — OOMKilled
T+5
02:19 AM — Root Cause Identified
Memory limit too low after recent feature deployment. Node pressure cascading to adjacent pods.
[RC] memory limit: 256Mi → required: 512Mi
T+10
02:24 AM — Mitigation Applied
HorizontalPodAutoscaler scaled up. Memory limits patched via Terraform. Affected node cordoned and drained.
kubectl patch deployment payment-service —memory 512Mi
T+15
02:29 AM — Resolved
All pods healthy. Traffic fully restored. Post-incident review scheduled.
[INCIDENT CLOSED] SEV-1 resolved in 15 minutes
🔍
Root Cause Analysis
Primary Cause: Memory limits set too low (256Mi) for payment-service after a new feature increased heap usage by 40%.
Contributing Factor: No memory-based HPA policy was in place; CPU-only scaling didn't trigger in time.
Why Users Weren't Affected: ArgoCD self-healing + pod disruption budgets maintained minimum replicas during the event.
Action 1
Memory-Based HPA
Added memory utilization metrics to HorizontalPodAutoscaler for all critical services.
Action 2
Resource Requests Audit
Quarterly review of all container resource requests/limits using VPA recommendations.
Action 3
Chaos Engineering
Monthly game days simulating OOMKills and node failures to validate auto-healing.
